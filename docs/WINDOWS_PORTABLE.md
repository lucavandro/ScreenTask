# Reproducing Windows portable builds

Run these commands from the repository root on Windows with the .NET 9 SDK.
The self-contained x64 build includes .NET and can run without installation:

```powershell
./scripts/Prepare-WebRtcRuntime.ps1
dotnet publish ScreenTask/ScreenTask.csproj -c Release -r win-x64 --self-contained true `
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true `
  -p:DebugType=None -p:DebugSymbols=false -o build/portable-win-x64
Copy-Item README.md build/portable-win-x64/
Compress-Archive -Path build/portable-win-x64/* `
  -DestinationPath build/ScreenTask-win-x64-portable.zip -Force
Get-FileHash build/ScreenTask-win-x64-portable.zip -Algorithm SHA256
```

Extract all ZIP contents into a folder before starting `ScreenTask.exe`. Close
any older running copy, including its notification-area instance. Do not copy
only the executable when the package contains accompanying notices or files.

For a smaller package that requires the matching .NET 9 Desktop Runtime **and
ASP.NET Core Runtime 9**, change
`--self-contained true` to `--self-contained false` and omit
`IncludeNativeLibrariesForSelfExtract`. The GitHub release workflow already
publishes standalone and framework-dependent variants when an explicit `vMAJOR.MINOR.PATCH`
release tag is pushed; an ordinary source push does not publish a release.

Generated binaries and ZIPs stay under the ignored `build/` directory. Git tracks
the sources and instructions, not the portable executable or local build output.
Once the GPU capture dependency is present, its `DirectX-NOTICE.txt` is copied by
the project into the publish folder and must remain in the distributed package.

`WebRTC-NOTICE.txt` is also copied into publish output and must accompany the
executable. The preparation script above embeds the app-local VC++ fallback for
clean PCs; see [WebRTC runtime details](WEBRTC_MODE.md).

## Publishing a GitHub release

Pushing source code or creating a tag alone does not provide downloadable binaries
until the release workflow completes successfully. The workflow publishes the
standalone EXE, framework-dependent ZIP, SHA-256 checksums and both dependency
notices as release assets in this repository.

For an existing tag (including the first release of a fork):

1. Open **Actions** in GitHub. If workflows are disabled for the fork, enable them.
2. Select **Publish GitHub Release → Run workflow** and leave the workflow branch
   on `master` so it uses the current publishing instructions.
3. Enter the existing tag, such as `v2.1.0`. The workflow checks out that exact tag
   and rejects a tag whose version differs from `ScreenTask.csproj`.
4. Wait for **Build, Verify & Publish Release** to succeed, then open
   [Releases](https://github.com/lucavandro/ScreenTask/releases) and expand **Assets**.

For a new version, update the source version first and push a matching
`vMAJOR.MINOR.PATCH` tag. This starts the same workflow automatically. An ordinary
branch push only runs CI. Do not move or recreate an existing tag to retry a build;
use the manual workflow instead. Publishing requires GitHub Actions and a workflow
token with `contents: write` permission.

The release workflow keeps generated packages under `build/release/` and also
uploads them as the `ScreenTask-Release-Packages` Actions artifact. Source-code
archives are generated by GitHub separately and are not runnable builds.
